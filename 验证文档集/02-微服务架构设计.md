## 一、总则

### 1.1 适用范围

本标准规范适用于公司所有采用微服务架构的新建及改造项目，明确了服务拆分的原则、流程、标准及验收要求，旨在提升系统可维护性、可扩展性及开发效率。

### 1.2 基本原则

服务拆分应遵循以下核心原则：

| 原则 | 说明 |
|------|------|
| 业务领域驱动 | 以业务能力边界为依据进行服务划分，确保每个服务聚焦单一业务职责 |
| 高内聚低耦合 | 服务内部功能模块应高度聚合，服务间依赖关系需最小化 |
| 独立部署与演进 | 每个微服务应具备独立部署能力，支持版本兼容性管理 |
| 数据一致性保障 | 明确服务边界内的数据归属，采用最终一致性或强一致性方案 |
| 性能与容量评估 | 拆分前需评估服务调用链性能瓶颈，预留扩展余量 |
| 监控与日志规范 | 服务间交互需标准化日志格式，部署集中监控告警系统 |

### 1.3 管理职责

技术管理部负责本标准的制定、修订与监督执行，各业务部门及研发团队负责具体的服务拆分实施工作。

## 二、系统整体架构

### 2.1 架构总览

系统采用分层微服务架构，从上到下分为：

1. **接入层**：Nginx 负载均衡 + API Gateway（Spring Cloud Gateway）
2. **应用层**：各业务微服务（用户服务、商品服务、订单服务、支付服务、库存服务、搜索服务、推荐服务、营销服务）
3. **中间件层**：消息队列（Kafka）、缓存（Redis Cluster）、搜索引擎（Elasticsearch）
4. **数据层**：MySQL（主从）、MongoDB、TiDB（分析型）
5. **基础设施层**：Kubernetes + Docker 容器化部署

### 2.3 服务拆分方案

#### 2.3.1 服务边界划分

以《业务能力清单》为基准，每个服务对应一个业务能力：

| 服务名称 | 服务职责 | 数据库 | 端口 | 团队 |
|---------|---------|--------|------|------|
| user-service | 用户注册、登录、个人信息管理 | user_db | 8081 | 用户团队 |
| product-service | 商品管理、品类管理、商品评价 | product_db | 8082 | 商品团队 |
| order-service | 订单创建、查询、取消、售后 | order_db | 8083 | 交易团队 |
| payment-service | 支付处理、退款、对账 | payment_db | 8084 | 支付团队 |
| inventory-service | 库存管理、扣减、回滚 | inventory_db | 8085 | 仓储团队 |
| search-service | 商品搜索、搜索建议 | ES | 8086 | 搜索团队 |
| recommendation-service | 个性化推荐、猜你喜欢 | MongoDB | 8087 | 推荐团队 |
| marketing-service | 优惠券、促销活动、积分 | marketing_db | 8088 | 营销团队 |
| notification-service | 短信、邮件、推送通知 | — | 8089 | 基础设施团队 |
| auth-service | 鉴权、Token管理、RBAC | auth_db | 8090 | 安全团队 |

#### 2.3.2 数据范围界定

- 服务内部数据表需满足 ACID 特性
- 禁止跨服务引用非主表数据
- 通过事件总线（Kafka）实现数据同步
- 采用 CQRS 模式分离读写模型

### 2.4 服务通信规范

#### 2.4.1 同步通信

| 场景 | 协议 | 格式 | 说明 |
|------|------|------|------|
| 外部API | HTTP/REST | JSON | 面向客户端的标准RESTful API |
| 内部服务调用 | gRPC | Protobuf | 高性能二进制协议 |
| 文件传输 | HTTP | Multipart | 大文件上传下载 |

**统一请求头规范**：

| Header字段 | 说明 | 示例 |
|-----------|------|------|
| X-Request-Id | 请求唯一标识（TraceID） | req-20260808-001 |
| X-Timestamp | 请求时间戳 | 1723084800 |
| X-Signature | 请求签名 | HMAC-SHA256 |
| X-App-Version | 应用版本号 | v4.0.0 |
| X-User-Token | 用户令牌 | JWT Token |

#### 2.4.2 异步通信

核心业务流程通过消息队列（Kafka）解耦，事件格式遵循 JSON Schema 标准。

**事件消息结构**：

```json
{
  "event_id": "evt-20260808-000001",
  "event_type": "order.created",
  "event_source": "order-service",
  "event_timestamp": "2026-08-08T10:00:00Z",
  "event_version": "1.0",
  "trace_id": "trace-abc123",
  "data": {
    "order_id": "DD2026080800001",
    "user_id": "U100001",
    "total_amount": 299.90,
    "items": [
      {"product_id": "P001", "quantity": 2, "price": 99.95}
    ]
  }
}
```

**核心事件列表**：

| 事件名称 | 生产者 | 消费者 | Topic | 说明 |
|---------|--------|--------|-------|------|
| order.created | order-service | inventory-service, payment-service, notification-service | order-events | 订单创建 |
| order.paid | payment-service | order-service, inventory-service, marketing-service | payment-events | 订单支付成功 |
| order.cancelled | order-service | inventory-service, payment-service, notification-service | order-events | 订单取消 |
| inventory.deducted | inventory-service | order-service, product-service | inventory-events | 库存扣减 |
| user.registered | user-service | marketing-service, notification-service | user-events | 用户注册 |

## 三、服务拆分流程

### 3.1 现状评估

收集现有系统架构文档、接口文档、性能测试报告，识别技术债及业务痛点。

### 3.2 初步拆分

基于业务领域模型，绘制服务依赖关系图，提出初步拆分方案。

### 3.3 方案评审

组织架构师、开发负责人、业务专家对拆分方案进行评审，重点评估：
- 技术可行性
- 数据迁移成本
- 运维复杂度

### 3.4 POC验证

选取典型场景进行最小可行验证，确认服务边界合理性及接口设计有效性。

### 3.5 分步实施

制定详细迁移计划，采用蓝绿部署或金丝雀发布策略，逐步完成服务拆分。

### 3.6 验收标准

| 验收项 | 标准 |
|--------|------|
| 服务功能完整性 | 所有功能模块通过验收测试 |
| 性能达标 | 接口 QPS ≥ 200 |
| 监控指标正常 | 错误率 < 0.1% |
| 日志可追踪 | 全链路日志覆盖率 100% |

## 四、数据治理标准

### 4.1 分库分表规则

按业务维度设计分表键：

| 服务 | 分表键 | 分表策略 | 分表数 | 说明 |
|------|--------|---------|--------|------|
| order-service | user_id | 取模 | 16 | 按用户ID分表 |
| inventory-service | product_id | 取模 | 8 | 按商品ID分库 |
| user-service | user_id | 范围 | 4 | 按ID范围分表 |
| payment-service | order_id | 取模 | 16 | 按订单ID分表 |

### 4.2 数据迁移方案

采用 Flink 或 MyCat 实现增量数据同步，迁移期间保留全量数据回滚能力。

**迁移步骤**：

1. **全量同步**：使用 DataX 将旧库数据全量同步到新分库
2. **增量同步**：通过 Canal 监听 binlog，实时同步增量数据
3. **数据校验**：采用 MD5 比对迁移前后数据一致性
4. **灰度切流**：先切 10% 流量到新库，观察无异常后逐步增加
5. **全量切流**：100% 流量切到新库，旧库保留 7 天作为回滚备份

### 4.3 分布式事务

| 方案 | 适用场景 | 实现方式 | 一致性 |
|------|---------|---------|--------|
| Saga | 跨服务业务流程 | 事件补偿模式 | 最终一致性 |
| TCC | 资金类操作 | Try-Confirm-Cancel | 强一致性 |
| 本地消息表 | 跨服务异步通知 | 消息表+定时轮询 | 最终一致性 |
| Seata AT | 跨库事务 | AT模式自动补偿 | 准强一致性 |

## 五、接口重构规范

### 5.1 版本管理策略

采用语义化版本控制（MAJOR.MINOR.PATCH），向后兼容 MINOR 版本变更。

| 版本变更 | 触发条件 | 兼容性 |
|---------|---------|--------|
| MAJOR | 破坏性变更（删除字段、修改语义） | 不向后兼容 |
| MINOR | 新增功能（新增字段、新增接口） | 向后兼容 |
| PATCH | 修复Bug | 完全兼容 |

### 5.2 接口降级方案

对核心接口配置熔断器（Sentinel），设置阈值：

| 参数 | 值 | 说明 |
|------|-----|------|
| 慢调用比例阈值 | 50% | 慢调用比例超过此值触发熔断 |
| 慢调用RT阈值 | 500ms | 响应时间超过此值判定为慢调用 |
| 最小请求数 | 5 | 统计窗口内最小请求数 |
| 熔断时长 | 10s | 熔断后等待恢复时间 |
| 恢复探测数 | 3 | 半开状态允许的探测请求数 |

### 5.3 接口文档标准

使用 Swagger/OpenAPI 3.0 自动生成文档，定期更新接口变更记录，业务方需通过测试环境验证。

## 六、运维监控要求

### 6.1 健康检查配置

服务启动时主动注册健康检查端点（/actuator/health），网关每 30 秒轮询一次状态。

**健康检查响应格式**：

```json
{
  "status": "UP",
  "components": {
    "db": {"status": "UP", "details": {"database": "MySQL", "result": 1}},
    "redis": {"status": "UP"},
    "kafka": {"status": "UP"},
    "diskSpace": {"status": "UP", "details": {"total": 107374182400, "free": 53687091200}}
  }
}
```

### 6.2 性能监控指标

| 指标名称 | 基线值 | 告警阈值 | 严重告警阈值 |
|---------|--------|---------|-------------|
| CPU利用率 | < 50% | > 70% | > 85% |
| 内存利用率 | < 60% | > 75% | > 90% |
| 磁盘利用率 | < 60% | > 80% | > 90% |
| 接口错误率 | < 0.1% | > 1% | > 5% |
| 接口P99延迟 | < 200ms | > 500ms | > 1000ms |
| GC停顿时间 | < 100ms | > 200ms | > 500ms |

### 6.3 日志管理规范

采用 ELK 日志系统，配置 Kibana 仪表盘展示核心业务链路日志。

**日志格式标准**：

```json
{
  "timestamp": "2026-08-08T10:00:00.000Z",
  "level": "INFO",
  "service": "order-service",
  "trace_id": "trace-abc123",
  "span_id": "span-def456",
  "method": "createOrder",
  "message": "Order created successfully",
  "extra": {
    "order_id": "DD2026080800001",
    "user_id": "U100001",
    "duration_ms": 45
  }
}
```

## 七、组织保障措施

### 7.1 架构委员会职责

每月召开架构评审会，处理跨团队技术争议，制定技术路线图。

### 7.2 技术培训计划

每季度组织微服务治理培训，内容涵盖：
- 服务熔断、限流、降级实战案例
- 分布式事务最佳实践
- Kubernetes 运维实操
- 性能调优方法论

### 7.3 代码质量管控

推行 SonarQube 静态扫描，禁止使用未封装的 HTTP 客户端，强制接口幂等性设计。

### 7.4 应急响应机制

建立服务故障 SLA：

| 故障级别 | 响应时间 | 解决时间 | 通知范围 |
|---------|---------|---------|---------|
| P0（系统不可用） | 5分钟 | 30分钟 | 全员通知 |
| P1（核心功能异常） | 10分钟 | 2小时 | 相关团队 |
| P2（非核心功能异常） | 30分钟 | 8小时 | 负责团队 |
| P3（轻微问题） | 2小时 | 24小时 | 值班人员 |

## 八、安全设计

### 8.1 认证与授权

| 安全层级 | 技术方案 | 说明 |
|---------|---------|------|
| 外部访问 | OAuth 2.0 + JWT | 第三方应用授权 |
| 用户认证 | JWT Token | 有效期2小时，支持刷新 |
| 服务间认证 | mTLS | 双向证书认证 |
| 权限控制 | RBAC | 基于角色的访问控制 |

### 8.2 数据安全

| 数据类型 | 存储安全 | 传输安全 | 展示安全 |
|---------|---------|---------|---------|
| 用户密码 | BCrypt加密 | TLS 1.2+ | 不展示 |
| 手机号 | AES-256加密 | TLS 1.2+ | 中间4位掩码 |
| 身份证号 | AES-256加密 | TLS 1.2+ | 中间8位掩码 |
| 银行卡号 | AES-256加密 | TLS 1.2+ | 只显示后4位 |
| 支付密码 | BCrypt加密 | TLS 1.2+ | 不展示 |
