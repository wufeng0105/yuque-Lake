## 一、总则

### 1.1 目的与适用范围

本手册旨在规范运维监控告警处理响应流程，提升系统稳定性与应急响应能力。适用于公司所有 IT 系统及网络设备的监控告警事件处理工作，包括但不限于服务器、数据库、网络设备、应用系统等。

### 1.2 基本原则

坚持"快速响应、有效处置、逐级上报、闭环管理"原则，确保告警事件得到及时、准确、规范的处置。

### 1.3 组织架构

成立告警处理领导小组，由信息技术部负责人担任组长，各系统负责人为成员。设立 24 小时值班制度，明确各岗位职责。

| 角色 | 职责 | 联系方式 |
|------|------|---------|
| 值班运维工程师（L1） | 首接告警、初步判断、基础处置 | 138-0000-0001 |
| 系统负责人（L2） | 深度分析、方案制定、执行修复 | 138-0000-0002 |
| 运维主管（L3） | 重大故障决策、资源协调、升级处理 | 138-0000-0003 |
| IT部门负责人（L4） | P0级故障总指挥、跨部门协调 | 138-0000-0004 |

## 二、告警分级标准

### 2.1 分级依据

根据告警事件的严重程度、影响范围、紧急程度等因素，将告警事件分为四个等级：

| 等级 | 名称 | 定义 | 影响范围 | 响应时效 |
|------|------|------|---------|---------|
| 一级 | 特别严重 | 系统完全瘫痪或核心业务中断 | 全公司 | 立即（5分钟内） |
| 二级 | 严重 | 系统部分功能异常或性能显著下降 | 部分业务 | 15分钟内 |
| 三级 | 一般 | 系统存在潜在风险或轻微异常 | 单个服务 | 30分钟内 |
| 四级 | 轻微 | 系统偶发性轻微异常 | 不影响业务 | 2小时内 |

### 2.2 一级告警判定标准

| 检测项 | 阈值 | 持续时间 | 说明 |
|--------|------|---------|------|
| 核心服务可用性 | < 95% | 1分钟 | 订单、支付、登录等核心服务 |
| 数据库主节点宕机 | 不可连接 | 即时 | MySQL Master节点 |
| API网关不可用 | 响应率 < 50% | 1分钟 | 全站入口 |
| 消息队列积压 | > 100,000条 | 5分钟 | Kafka消费滞后 |
| 磁盘空间 | > 95% | 即时 | 任何核心服务器 |

### 2.3 二级告警判定标准

| 检测项 | 阈值 | 持续时间 | 说明 |
|--------|------|---------|------|
| 服务接口错误率 | > 5% | 2分钟 | 非核心服务 |
| CPU利用率 | > 85% | 5分钟 | 任何服务器 |
| 内存利用率 | > 90% | 3分钟 | 任何服务器 |
| 慢查询数 | > 100/分钟 | 5分钟 | 数据库 |
| Redis连接数 | > 80%最大连接 | 3分钟 | 缓存集群 |

## 三、告警接收与确认

### 3.1 接收渠道

通过以下监控平台实时接收告警信息：

| 监控平台 | 监控对象 | 告警方式 | 值班安排 |
|---------|---------|---------|---------|
| Prometheus + Alertmanager | 服务器、容器、应用 | 钉钉机器人 + 短信 + 电话 | 7×24小时 |
| Zabbix | 网络设备、机房环境 | 邮件 + 短信 | 7×24小时 |
| ELK Stack | 应用日志 | 钉钉机器人 | 工作时间 |
| 阿里云云监控 | 云资源 | 短信 + 钉钉 | 7×24小时 |
| 自研监控平台 | 业务指标 | 钉钉机器人 + 邮件 | 工作时间 |

### 3.2 确认流程

1. 值班人员接到告警后，需在 **5分钟内** 确认告警有效性，避免误报
2. 确认无效的告警需记录并分析原因，优化监控规则
3. 确认有效的告警需立即记录告警时间、级别、影响系统等信息

### 3.3 记录要求

建立告警事件台账，内容包括：

| 记录字段 | 说明 | 示例 |
|---------|------|------|
| 告警ID | 唯一标识 | ALT-20260808-001 |
| 告警时间 | 首次触发时间 | 2026-08-08 10:00:00 |
| 告警级别 | 一/二/三/四级 | 二级 |
| 告警来源 | 监控平台名称 | Prometheus |
| 影响系统 | 受影响的系统/服务 | order-service |
| 告警内容 | 详细描述 | 接口错误率 8.5%，超过阈值 5% |
| 处理人 | 接手处理的工程师 | 张三 |
| 处理状态 | 待处理/处理中/已解决/已关闭 | 已解决 |
| 解决时间 | 故障恢复时间 | 2026-08-08 10:25:00 |
| 根因分析 | 故障原因 | 数据库连接池耗尽 |
| 处理措施 | 具体操作 | 扩容连接池、重启服务 |

## 四、告警处理流程

### 4.1 分级响应

| 告警级别 | 响应人员 | 响应时效 | 处理时效 | 上报要求 |
|---------|---------|---------|---------|---------|
| 一级 | L1→L2→L3→L4 | 立即 | 1小时初步处置 | 每小时向领导小组汇报 |
| 二级 | L1→L2 | 15分钟 | 4小时完成 | 每半天向部门负责人汇报 |
| 三级 | L1 | 30分钟 | 24小时内分析处理 | 纳入周报 |
| 四级 | L1 | 2小时 | 定期汇总处理 | 纳入月报 |

### 4.2 处置步骤

**步骤一：分析告警根源**

结合日志、监控数据、用户反馈等多维度信息，定位问题：

1. 查看告警详情面板，确认告警指标和阈值
2. 查看关联监控图表（CPU、内存、网络、磁盘）
3. 查看应用日志（ELK 搜索相关 trace_id）
4. 查看链路追踪（SkyWalking 定位慢调用）
5. 查看最近变更记录（是否因发布引起）

**步骤二：制定处置方案**

根据问题性质选择策略：

| 问题类型 | 处置策略 | 操作步骤 |
|---------|---------|---------|
| 资源不足 | 扩容 | 1.增加Pod副本数 2.扩容数据库 3.增加缓存节点 |
| 代码Bug | 回滚 | 1.确认最近发布版本 2.执行回滚操作 3.通知研发修复 |
| 配置错误 | 修复配置 | 1.定位错误配置 2.修改配置中心 3.重启服务 |
| 网络异常 | 隔离+排查 | 1.隔离故障节点 2.排查网络设备 3.联系网络管理员 |
| 依赖故障 | 降级 | 1.启用降级开关 2.使用备选方案 3.通知依赖方 |

**步骤三：执行处置措施**

严格按照操作规程操作，避免二次故障：

1. 任何操作前必须备份关键数据
2. 重大操作需经两人复核
3. 操作过程中需详细记录每一步骤
4. 处置完成后需进行功能验证和性能测试

**步骤四：验证处置效果**

1. 确认告警已自动恢复
2. 验证核心业务功能正常
3. 观察监控指标 15 分钟无异常
4. 通知相关方故障已恢复

### 4.3 协作机制

| 协作类型 | 适用场景 | 协作方式 |
|---------|---------|---------|
| 跨部门协作 | 涉及多个系统的告警 | 建立联动机制，明确牵头部门 |
| 技术支持 | 需要外部技术专家协助 | 联系厂商技术支持或行业专家 |
| 信息通报 | 处理过程中信息同步 | 通过钉钉群实时通报处理进展 |

## 六、告警处置规范

### 6.1 操作规程

1. 任何操作前必须备份关键数据（数据库快照、配置文件备份）
2. 重大操作需经两人复核（操作人 + 复核人）
3. 操作过程中需详细记录每一步骤（操作时间、操作内容、执行结果）
4. 处置完成后需归档所有文档（告警记录、处置过程、根因分析）

### 6.2 资源调配

| 告警级别 | 人力资源调配 | 预算权限 |
|---------|-------------|---------|
| 一级 | 全体运维人员参与，必要时召回休假人员 | 可临时申请额外预算 |
| 二级 | 至少2名运维工程师处理 | 部门内调配 |
| 三级 | 值班人员处理 | 无需额外预算 |
| 四级 | 纳入定期维护计划 | 无需额外预算 |

### 6.3 事后复盘

一级、二级告警处置完成后，需在 **48小时内** 召开复盘会议：

| 复盘项 | 内容 |
|--------|------|
| 故障时间线 | 从告警触发到完全恢复的完整时间线 |
| 根因分析 | 使用5Why分析法，找到根本原因 |
| 处置评估 | 评估处置过程中的优点和不足 |
| 改进措施 | 制定具体的改进措施和跟进计划 |
| 知识沉淀 | 更新FAQ、操作手册、应急预案 |

## 七、监控告警配置规范

### 7.1 告警规则配置

**Prometheus 告警规则示例**：

```yaml
groups:
  - name: service_alerts
    rules:
      - alert: HighErrorRate
        expr: |
          sum(rate(http_requests_total{status=~"5.."}[2m])) by (service)
          / sum(rate(http_requests_total[2m])) by (service)
          > 0.05
        for: 2m
        labels:
          severity: critical
        annotations:
          summary: "{{ $labels.service }} 错误率过高"
          description: "{{ $labels.service }} 接口错误率 {{ $value }}%，超过阈值 5%"

      - alert: HighCPU
        expr: |
          100 - avg(increase(node_cpu_seconds_total{mode="idle"}[5m])) by (instance) * 100 / 300
          > 85
        for: 5m
        labels:
          severity: warning
        annotations:
          summary: "{{ $labels.instance }} CPU 使用率过高"
          description: "CPU 使用率 {{ $value }}%，超过阈值 85%"
```

### 7.2 告警通知模板

| 通知渠道 | 模板内容 |
|---------|---------|
| 钉钉 | 🔴【{{.severity}}】{{.alertname}}\n服务：{{.service}}\n实例：{{.instance}}\n详情：{{.description}}\n时间：{{.startsAt}}\n处理：https://monitor.example.com/alert/{{.id}} |
| 短信 | 【告警】{{.severity}}级 {{.alertname}} 服务：{{.service}} 详情：{{.description}} 时间：{{.startsAt}} |
| 电话 | 自动语音播报：{{.severity}}级告警，{{.alertname}}，服务{{.service}}异常，请立即处理。 |

## 八、常用运维操作手册

### 8.1 服务扩缩容

| 操作场景 | 操作命令 | 验证方式 |
|---------|---------|---------|
| 扩容Pod | `kubectl scale deployment order-service --replicas=5` | `kubectl get pods -l app=order-service` |

| 操作场景 | 操作步骤 | 风险等级 |
|---------|---------|---------|

## 九、附录

### 附录A：常见问题处理（FAQ）

| 问题现象 | 可能原因 | 处理方法 |
|---------|---------|---------|
| 服务无法启动 | 配置错误/端口冲突/依赖服务不可用 | 检查配置、排查端口、确认依赖 |
| 接口超时 | 数据库慢查询/网络延迟/资源不足 | 排查慢查询、检查网络、扩容资源 |
| 内存溢出（OOM） | 内存泄漏/堆内存不足 | 增加堆内存、排查内存泄漏、重启服务 |
| 磁盘满 | 日志文件过大/临时文件未清理 | 清理日志、扩容磁盘、配置日志轮转 |
| CPU飙高 | 死循环/大量计算/GC频繁 | 抓取线程栈、分析火焰图、优化代码 |
