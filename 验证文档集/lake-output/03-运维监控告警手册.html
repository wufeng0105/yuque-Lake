运维监控告警处理响应手册

文档版本：v2.1.0 文档状态：正式发布 编写日期：2026-08-08 编写人：运维部

一、总则

1.1 目的与适用范围

本手册旨在规范运维监控告警处理响应流程，提升系统稳定性与应急响应能力。适用于公司所有 IT 系统及网络设备的监控告警事件处理工作，包括但不限于服务器、数据库、网络设备、应用系统等。

1.2 基本原则

坚持"快速响应、有效处置、逐级上报、闭环管理"原则，确保告警事件得到及时、准确、规范的处置。

1.3 组织架构

成立告警处理领导小组，由信息技术部负责人担任组长，各系统负责人为成员。设立 24 小时值班制度，明确各岗位职责。

角色职责联系方式
值班运维工程师（L1）首接告警、初步判断、基础处置138-0000-0001
系统负责人（L2）深度分析、方案制定、执行修复138-0000-0002
运维主管（L3）重大故障决策、资源协调、升级处理138-0000-0003
IT部门负责人（L4）P0级故障总指挥、跨部门协调138-0000-0004

二、告警分级标准

2.1 分级依据

根据告警事件的严重程度、影响范围、紧急程度等因素，将告警事件分为四个等级：

等级名称定义影响范围响应时效
一级特别严重系统完全瘫痪或核心业务中断全公司立即（5分钟内）
二级严重系统部分功能异常或性能显著下降部分业务15分钟内
三级一般系统存在潜在风险或轻微异常单个服务30分钟内
四级轻微系统偶发性轻微异常不影响业务2小时内

2.2 一级告警判定标准

检测项阈值持续时间说明
核心服务可用性< 95%1分钟订单、支付、登录等核心服务
数据库主节点宕机不可连接即时MySQL Master节点
API网关不可用响应率 < 50%1分钟全站入口
消息队列积压> 100,000条5分钟Kafka消费滞后
磁盘空间> 95%即时任何核心服务器

2.3 二级告警判定标准

检测项阈值持续时间说明
服务接口错误率> 5%2分钟非核心服务
CPU利用率> 85%5分钟任何服务器
内存利用率> 90%3分钟任何服务器
慢查询数> 100/分钟5分钟数据库
Redis连接数> 80%最大连接3分钟缓存集群

3.1 接收渠道

监控平台监控对象告警方式值班安排

自研监控平台业务指标钉钉机器人 + 邮件工作时间

3.2 确认流程

  1. 值班人员接到告警后，需在 5分钟内 确认告警有效性，避免误报
  2. 确认无效的告警需记录并分析原因，优化监控规则
  3. 确认有效的告警需立即记录告警时间、级别、影响系统等信息

四、告警处理流程

4.1 分级响应

告警级别响应人员响应时效处理时效上报要求
一级L1→L2→L3→L4立即1小时初步处置每小时向领导小组汇报
二级L1→L215分钟4小时完成每半天向部门负责人汇报
三级L130分钟24小时内分析处理纳入周报
四级L12小时定期汇总处理纳入月报

4.2 处置步骤

步骤一：分析告警根源

结合日志、监控数据、用户反馈等多维度信息，定位问题：

  1. 查看告警详情面板，确认告警指标和阈值
  2. 查看关联监控图表（CPU、内存、网络、磁盘）
  3. 查看应用日志（ELK 搜索相关 trace_id）
  4. 查看链路追踪（SkyWalking 定位慢调用）
  5. 查看最近变更记录（是否因发布引起）

步骤二：制定处置方案

根据问题性质选择策略：

问题类型处置策略操作步骤
资源不足扩容1.增加Pod副本数 2.扩容数据库 3.增加缓存节点
代码Bug回滚1.确认最近发布版本 2.执行回滚操作 3.通知研发修复
配置错误修复配置1.定位错误配置 2.修改配置中心 3.重启服务
网络异常隔离+排查1.隔离故障节点 2.排查网络设备 3.联系网络管理员
依赖故障降级1.启用降级开关 2.使用备选方案 3.通知依赖方

步骤三：执行处置措施

严格按照操作规程操作，避免二次故障：

  1. 任何操作前必须备份关键数据
  2. 重大操作需经两人复核
  3. 操作过程中需详细记录每一步骤
  4. 处置完成后需进行功能验证和性能测试

步骤四：验证处置效果

  1. 确认告警已自动恢复
  2. 验证核心业务功能正常
  3. 观察监控指标 15 分钟无异常
  4. 通知相关方故障已恢复

4.3 协作机制

协作类型适用场景协作方式
跨部门协作涉及多个系统的告警建立联动机制，明确牵头部门
技术支持需要外部技术专家协助联系厂商技术支持或行业专家
信息通报处理过程中信息同步通过钉钉群实时通报处理进展

五、应急响应预案

5.1 一级告警应急措施

数据库主节点宕机：

步骤操作负责人预计时间
1确认主节点状态，检查是否可快速恢复L1值班2分钟
2启动主从切换流程L2系统负责人5分钟
3修改应用数据源指向新主节点L2系统负责人3分钟
4验证服务恢复正常L1值班5分钟
5排查原主节点故障原因L2系统负责人30分钟
6恢复原主节点作为从节点L2系统负责人60分钟

核心服务不可用：

步骤操作负责人预计时间
1确认故障范围，隔离故障节点L1值班3分钟

措施类型具体操作执行人

资源临时扩容增加Pod副本、扩容缓存L1值班

六、告警处置规范

6.1 操作规程

  1. 任何操作前必须备份关键数据（数据库快照、配置文件备份）
  2. 重大操作需经两人复核（操作人 + 复核人）
  3. 操作过程中需详细记录每一步骤（操作时间、操作内容、执行结果）
  4. 处置完成后需归档所有文档（告警记录、处置过程、根因分析）

6.2 资源调配

告警级别人力资源调配预算权限
一级全体运维人员参与，必要时召回休假人员可临时申请额外预算
二级至少2名运维工程师处理部门内调配
三级值班人员处理无需额外预算
四级纳入定期维护计划无需额外预算

6.3 事后复盘

一级、二级告警处置完成后，需在 48小时内 召开复盘会议：

复盘项内容
故障时间线从告警触发到完全恢复的完整时间线
根因分析使用5Why分析法，找到根本原因
处置评估评估处置过程中的优点和不足
改进措施制定具体的改进措施和跟进计划
知识沉淀更新FAQ、操作手册、应急预案

七、监控告警配置规范

7.1 告警规则配置

Prometheus 告警规则示例：

groups: - name: service_alerts rules: - alert: HighErrorRate expr: | sum(rate(http_requests_total{status=~"5.."}[2m])) by (service) / sum(rate(http_requests_total[2m])) by (service) > 0.05 for: 2m labels: severity: critical annotations: summary: "{{ $labels.service }} 错误率过高" description: "{{ $labels.service }} 接口错误率 {{ $value }}%，超过阈值 5%" - alert: HighCPU expr: | 100 - avg(increase(node_cpu_seconds_total{mode="idle"}[5m])) by (instance) * 100 / 300 > 85 for: 5m labels: severity: warning annotations: summary: "{{ $labels.instance }} CPU 使用率过高" description: "CPU 使用率 {{ $value }}%，超过阈值 85%"
